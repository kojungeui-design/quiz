# Battery Design Studio v8

배터리 신규 설계 자동화 워크벤치. 사내 실적 DB를 근거로 목표 성능에 맞는 극판 조합·매수를 설계하고,
라인업 공용화와 원가를 비교합니다.

**구버전(v7)을 개선한 것이 아니라 처음부터 다시 만들었습니다.** 계산 엔진만 이식했고, 나머지는 새로 썼습니다.

---

## 빠르게 시작하기

**쓰기만 할 때** — `dist\배터리설계스튜디오.html` 을 더블클릭하면 끝입니다.
파일 하나로 완결되어 있어서 어디든 복사해도 그대로 열립니다. 인터넷도 필요 없습니다.

**고쳐서 다시 만들 때** — `빌드하기.bat` 더블클릭.

```
dist\배터리설계스튜디오.html        사내용 (약 0.38 MB)
dist\배터리설계스튜디오_시연용.html  단가·판매수량 마스킹본
```

Node.js(LTS)만 있으면 됩니다. **npm install이 필요 없습니다** — 외부 패키지를 하나도 쓰지 않습니다.

> DB만 자주 갱신해서 앱 파일을 다시 배포하기 번거롭다면 `node build.mjs --split` 을 쓰세요.
> 데이터가 `dist\data\bds-db.js` 로 빠지고, 그때는 **dist 폴더를 통째로** 전달해야 합니다.
> 기본값이 단일 파일인 이유는, 파일 하나만 옮기면 되는 편의가 DB 갱신 편의보다 크기 때문입니다.

### 고친 계산 버그 (구버전에서 실제로 나던 것)

1. **목표값을 비우면 성능여유가 `Infinity%`로 출력**됐습니다 → 계산 불가를 `null`로 표시하고, 애초에 계산을 시작하지 않습니다.
2. **호환 극판이 없을 때 공용화율이 133%**로 나왔습니다 → 0%로 바로잡았습니다.
3. **12V 6셀이 상수로 박혀** 6V·24V 제품 원가가 틀렸습니다 → 셀 수를 입력값으로 뺐습니다.
4. **제품을 표시명으로 식별**해 이름이 겹치면 근거가 뒤섞였습니다 → 내부 uid로 식별합니다.
5. **신형 양극 단가를 기판비 55% 고정으로 분할**했습니다 → 극판 마스터 120종 회귀(R² 0.973) 기준
   실제 기판 비중은 평균 40.7%(31~50%)라, 신형안(1·2안) 원가가 실제보다 싸게 나왔습니다.
   극판별 실측 비중으로 바꿨고, 기존 극판안(3안)은 영향이 없습니다.

각 버그는 `test/bugfix.test.mjs`에서 "구엔진은 이렇게 틀렸다 → 신엔진은 이렇다" 형태로 고정해 두었습니다.

## 검증 방식

```
node --test test/*.test.mjs
```

세 층으로 검증합니다.

**1. 엔진 대조 (parity.test.mjs)** — 구버전 HTML에서 계산 엔진만 도려내(`test/tools/extract-legacy-engine.mjs`)
실행 가능한 모듈로 만든 뒤, 신엔진과 숫자를 맞춰봅니다. 83개 제품군 전수 × 3개 설계안,
83개 제품 대형 라인업 × 3개 관점, 기준품 지정 경로, 차단 경로, DB 백테스트, 통계까지 **완전 일치**를 요구합니다.
이식 과정에서 수식이 틀어지면 즉시 잡힙니다.

**2. 화면 동작 (app-smoke.test.mjs)** — 브라우저 없이 최소 DOM(`test/dom-stub.mjs`) 위에서 앱을 띄워
7개 화면을 모두 그리고, 과제 생성 → 입력 → 계산 → 설계안 선택 → 저장까지 태웁니다.
저장 실패(용량 초과) 상황도 강제로 만들어 사용자에게 알리는지 확인합니다.

**3. 배포본 (build.test.mjs)** — 소스가 아니라 `dist`의 HTML을 그대로 읽어 실행합니다.
빌드 과정에서 깨지지 않았는지, 데이터가 HTML에 새어 들어가지 않았는지, 외부 요청이 없는지 확인합니다.

**4. DB 임포트 (dbsource.test.mjs)** — 잘못된 데이터를 **반려하는 쪽**을 더 촘촘히 고정합니다.
없는 극판 참조, 코드 중복, 매수 이상, 치수 누락이 각각 걸리는지, 정상 행만 골라 살리는지,
병합·대체가 기존 데이터를 정확히 어떻게 건드리는지, 내장 DB 객체가 변형되지 않는지를 봅니다.
마지막으로 임포트한 제품군으로 설계안이 실제 계산되는 데까지 태웁니다 — 임포트만 되고
예측에 반영되지 않으면 아무 의미가 없기 때문입니다(구버전이 정확히 그 상태였습니다).

## 데이터 다루기

DB를 갱신하는 길은 두 가지입니다. 둘 다 같은 정합성 검사를 통과해야 반영됩니다.

### 1. 앱 안에서 — 설계자가 직접 (Node 불필요)

`제품·극판 DB` 화면의 **사내 DB 갱신**에서 CSV(또는 JSON)를 올리면 됩니다.
내장 DB를 고치는 게 아니라 그 위에 덮는 방식이라, 언제든 해제하면 원래대로 돌아옵니다.

```
내장 DB (빌드 산출물)  +  임포트 DB (브라우저 저장)  →  예측 엔진이 쓰는 DB
```

- 열 이름은 한글·영문 모두 인식합니다 — `제품코드`/`code`, `조립매수`/`assembly`, `양극코드`/`posCode` …
  파일이 제품인지 극판인지는 열 구성을 보고 알아서 판별합니다.
- **제품이 새 극판을 쓰면 극판 파일과 제품 파일을 함께 올리세요.** 따로 올리면 아직 없는 극판을
  참조한다며 반려됩니다.
- **병합**은 같은 코드만 덮어쓰고 나머지는 그대로 둡니다. **대체**는 올린 종류를 통째로 바꿉니다.
- 반려된 행은 사유와 행 번호가 표에 나오고 CSV로 받을 수 있습니다. 정상 행만 먼저 반영해도 됩니다.
- `현재 제품 내보내기`로 지금 DB를 같은 열 이름의 CSV로 받아, 고쳐서 다시 올리는 왕복이 됩니다.

DB가 바뀌면 저장된 과제의 계산 결과는 근거가 달라지므로 전부 "재계산 필요"로 되돌아갑니다.
옛 근거로 결재가 올라가지 않게 하기 위한 것이니, 결재 전에 다시 계산하세요.

> **한계** — 임포트 DB는 브라우저 localStorage(약 5MB, 과제와 공유)에 저장되고 **그 PC에만** 남습니다.
> 팀 전체에 반영하려면 아래 2번으로 배포본을 다시 만들어 돌리세요. 용량이 부족하다는 메시지가 뜨면
> 제품군을 나눠 올리거나 2번으로 넘어가야 합니다.

### 2. 소스에서 — 배포본에 싣기

`data/source/`의 JSON을 고치고 `빌드하기.bat`을 다시 돌리면 됩니다.
데이터는 소스에서 분리되어 있으므로, 앱 코드를 건드리지 않고 DB만 갱신할 수 있습니다.

빌드 시 정합성을 검사해, 극판 참조가 깨졌거나 제품 코드가 중복되면 배포본을 만들지 않고 멈춥니다.
앱 안 임포트도 **같은 규칙**을 쓰므로, 1번에서 통과한 데이터는 `data/source`에 넣어도 그대로 빌드됩니다.

### 대외비 주의

`배터리설계스튜디오.html`에는 **극판 단가와 제품별 판매수량**이 들어 있습니다. 사외 반출 금지.

외부 시연에는 함께 생성되는 `배터리설계스튜디오_시연용.html`을 쓰세요.
단가를 중앙값 대비 상대비율로, 판매수량을 구간값으로 바꾼 파일이며 화면 위쪽에 마스킹본 표시가 항상 뜹니다.

## 납중량 계산

설계안마다 납중량(kg)을 함께 계산합니다.

```
납중량 = 기판납 + 활물질납 + COS납(스트랩·포스트)
  기판납   = 기판중량 × 매수 × 셀수          (신형 양극은 0.7T 환산 중량으로)
  활물질납 = 활물질중량 ÷ 1.04 ÷ (양극 1.195 | 음극 1.175)
  COS납   = max(0, −0.386×(셀수/6) + 0.608×기판납)   ← 실측 잔차 회귀
```

- 계수는 실측 납중량이 있는 제품 **735건으로 적합**했습니다: 평균오차 3.9%, P90 8.3%.
  `test/lead.test.mjs` 가 이 정확도의 퇴행을 막습니다(MAPE 4.5% 상한).
- **기준품 고정 설계(3안에서 기준품 직접 지정)는 등록 실측값을 그대로 씁니다.** 화면의 `*` 표시가
  모델 추정임을 뜻하고, 분해 내역(기판/활물질/COS)은 마우스를 올리면 보입니다.
- 셀수를 반영합니다 — 6V(3셀)·24V(12셀) 제품도 맞게 계산됩니다.

## 격리판 봉합 극성

봉합이 (+)극판인지 (−)극판인지는 **설계자가 고르는 값이 아니라 극판 조합이 정하는 파생값**입니다.
사내 실적 9,319건을 분석해 확인했습니다.

| 무엇으로 맞히나 | 적중률 |
|---|---|
| 무조건 (−)봉합 (기준선) | 88.1% |
| "EFB·LN이면 (+)" 같은 규칙 | 74.3% ← 기준선보다 나쁨 |
| 제품군 실적 | 95.0% |
| **극판 조합 실적** | **99.7%** |

그래서 규칙을 쓰지 않고 실적에서 끌어옵니다. 판정 순서는 **극판 조합 → 제품군 → 판단 불가**이며,
근거가 없으면 추측하지 않고 `판단 불가`로 둡니다.

- 설계안을 계산하면 BOM 표와 보고서에 **봉합 열**이 자동으로 붙습니다. 입력할 것은 없습니다.
- 실적에 소수 예외가 섞인 조합은 `⚠` 를 붙여 확인을 요청합니다(마우스를 올리면 근거 건수가 보입니다).
- 신형 극판 설계(1·2안)도 원본 극판 조합의 봉합을 따릅니다 — 같은 크기 극판을 다시 만드는 것이라
  봉합 방식이 바뀔 이유가 없기 때문입니다.
- (+)봉합은 EFB 계열과 유럽 규격(LN·LBN·EN)에 몰려 있습니다.

## 실시간 설계 조절 (what-if)

설계안을 계산하고 나면 `설계·BOM·공용화` 화면 아래에 **실시간 설계 조절** 카드가 붙습니다.
슬라이더 네 개를 움직이면 그 자리에서 다시 계산됩니다.

| 조절 항목 | 범위 | 무엇이 따라 움직이나 |
| --- | --- | --- |
| 양극 기판두께 | 0.50 – 1.30T | 기판납, CCA(두께계수), 원가 |
| 음극 기판두께 | 0.50 – 1.30T | 기판납, CCA(두께계수), 원가 |
| 양극 활물질 | 실적범위 ±30% | C20·RC, 활물질납, 원가 |
| 조립매수 | DB 실적범위 ±3~4매 | 전 항목 + 극판 배분 |

납중량은 **기판 / 활물질 / COS 로 쪼개서** 같이 보여주므로, 늘어난 납이 어디서 왔는지 바로 보입니다.

### 라인업 전체가 함께 움직입니다

제품이 여러 개면 카드 위쪽에서 제품을 고를 수 있고, **조절값은 제품마다 따로 유지됩니다** —
제품을 오가며 비교해도 만져둔 값이 날아가지 않습니다. 그리고 제품 하나만 조절해도
아래 라인업 표가 함께 다시 계산됩니다.

| 라인업 항목 | 왜 움직이나 |
| --- | --- |
| 가중 평균원가 | 제품별 원가가 연간 물량으로 가중되므로, 물량 큰 제품을 만질수록 크게 움직입니다 |
| 목표 충족 제품 | 조절 때문에 목표를 놓치는 제품이 생기면 바로 줄어듭니다 |
| 연간 납 소요량 | 대당 납중량 × 연간 물량. 라인업 전체 납 구매량이 몇 톤 늘고 주는지 |
| 공용 극판군 · 개발 투자 | 금형비는 극판군마다 1회 발생하고, 그 극판군을 쓰는 물량 전체에 나눠 실립니다 |

라인업 집계는 정식 계산(`buildPlan`)과 **같은 집계 함수**를 씁니다. 두 곳에서 따로 계산하면 언젠가 어긋나기 때문입니다.

> **함께 고친 것** — 3안(기존 극판)은 등록 단가를 그대로 쓰기 때문에, 조절로 두께나 활물질을 바꿔도
> 단가가 꿈쩍하지 않았습니다. 조절하면 더 이상 그 극판이 아니므로, 신형 극판과 같은 방식
> (기판비·활물질비 비중별 변화율)으로 단가를 환산하게 했습니다. 조절이 없을 때는 종전 값 그대로입니다.

지켜야 할 전제가 셋 있습니다.

1. **여기서 바꾼 값은 저장되지 않습니다.** 검토용 탐색이며, 확정하려면 요구사양을 고쳐 정식으로 다시 계산해야 합니다.
   결재 문서로 흘러가면 안 되는 값이기 때문에 일부러 화면에만 둡니다.
2. **확정 설계가 기준품 실측값을 그대로 쓰고 있었다면**(3안에서 기준품을 직접 지정한 경우) 조절을 시작하는 순간
   계산이 실측 → 모델로 넘어갑니다. 그 차이를 조절 효과로 오해하지 않도록, 「기준값」 열도 같은 모델로 한 번
   돌린 값을 싣고 변화량은 모델끼리만 비교합니다. 화면에도 그 사실을 알립니다.
3. **실적 범위를 벗어나면 막지 않고 알립니다.** 활물질 상·하한, DB 실적 매수범위, 입력한 최대 허용매수,
   그리고 "그 두께의 극판이 실제로 있는지 확인 필요"를 각각 경고합니다. 기판두께는 근사 모델(CCA 두께계수
   −14%~+4%)을 거치므로 시제품 검증이 필요합니다.

## 예측 보정 (시제품 실측 되먹임)

백테스트는 DB가 자기 자신을 재현하는 하한선일 뿐입니다. 도구가 실제로 정확해지는 길은
시제품 실측을 예측식에 되먹이는 것뿐이고, `예측 보정` 화면이 그 고리입니다.

```
실측 등록 (n≥5)  →  1차식 적합 (실측 = a×예측 + b)  →  승인  →  모든 예측에 적용
```

- **승인 전에는 어떤 경우에도 예측에 반영되지 않습니다.** 초안 적합은 참고용입니다.
- 승인에는 조건이 있습니다: 표본 5건 이상, 기울기 0.5~1.5, **무보정보다 오차가 줄어들 것**.
  조건을 만족하지 않으면 승인 버튼이 비활성화되고 사유가 표시됩니다.
- 표본을 더하거나 지우면 승인이 자동으로 풀립니다. 승인한 사람이 본 데이터와
  적용되는 데이터가 달라지는 일을 막기 위해서입니다.
- 보정은 예측값에만 적용됩니다. 기준품을 그대로 쓰는 3안 고정 경로의 등록 실측값은
  건드리지 않고, 활물질 역산은 보정 후 값이 목표를 넘도록 일관되게 계산됩니다.
- 적용 여부는 사이드바 배지와 보고서 "근거와 한계"에 항상 표기됩니다. 보정된 숫자가
  보정 표시 없이 결재에 올라가는 일은 없습니다.
- 보정을 켜고 끄면 저장된 과제의 계산 결과는 전부 "재계산 필요"로 되돌아갑니다.

## 알려진 한계

- 케이스 도면·단자 위치·패킹 호환성은 판정하지 않습니다.
- 매수 탐색은 DB 실적 매수범위 안에서만 이뤄집니다.
- 원가는 극판 재료비·조립비 중심의 비교값이며 견적가가 아닙니다.
- CCA 두께계수(0.86~1.04 clamp)는 실적 회귀가 아닌 보수적 근사입니다.
- 과제는 브라우저 localStorage(약 5MB)에만 저장됩니다. 공유하려면 백업 파일로 주고받아야 합니다.
- 앱 안에서 올린 임포트 DB도 같은 localStorage를 쓰며 그 PC에만 남습니다. 팀 공통 DB로 만들려면
  `data/source`에 넣어 다시 빌드해 배포해야 합니다.
- 예측 보정은 지표별 1차식(전역)입니다. 제품군별·온도별로 따로 보정하지는 않으므로,
  시험조건이 다른 실측을 한 지표에 섞으면 안 됩니다.
- 이 도구는 설계 검토 지원용이며 시제품 시험과 Gate 승인을 대체하지 않습니다.
